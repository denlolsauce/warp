# Warp Survey — local infrastructure

Local development stack for the standalone Warp Survey product. Everything
here is deliberately isolated from the existing Warp product: separate
database, separate Redis, separate object storage, separate credentials, and
non-default host ports so both stacks can run side by side.

## Services

| Service  | Image              | Host port | Purpose                                  |
| -------- | ------------------ | --------- | ---------------------------------------- |
| postgres | postgres:16-alpine | 5433      | Application database (Prisma)            |
| redis    | redis:7-alpine     | 6380      | Job queue, outbox, rate limiting         |
| minio    | minio/minio        | 9000/9001 | S3-compatible object storage (private)   |

`minio-init` runs once to create the private `warp-survey-dev` bucket and set
CORS so the browser can PUT multipart parts directly (with `ETag` exposed —
required to complete a multipart upload).

## Usage

```bash
cd warp-survey/infra
docker compose up -d

# Then, from warp-survey/apps/web:
cp .env.example .env    # fill AUTH_SECRET, SMTP, WORKER_CALLBACK_SECRET
pnpm prisma migrate dev
pnpm prisma db seed
```

Data is persisted under `infra/.data/` (git-ignored). `docker compose down -v`
plus deleting `.data/` gives a clean slate.

## Production notes (pilot)

- **Web app**: always-on CPU deployment (any Node 20+ host). Postgres and
  Redis must be managed instances dedicated to this product.
- **Object storage**: a private S3-compatible bucket in an EU region for the
  pilot. All access goes through short-lived signed URLs generated by the web
  app; the bucket must never be public and permanent URLs must never be
  stored or shared.
- **Pipeline worker** (`services/pipeline`): containerised Python worker on
  CPU/GPU capacity as stages require. It consumes the Redis queue
  (language-neutral JSON messages validated against
  `packages/contracts/schema/`), leases jobs with heartbeats and fencing
  tokens, and reports stage status to the web app's
  `/api/v1/worker/stage-status` callback using `WORKER_CALLBACK_SECRET`.
- **Secrets**: never share credentials with the existing Warp product, and
  never place secrets in client code.
